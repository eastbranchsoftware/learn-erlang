The chat room from lesson 09 kept a dead member in its list because a send to a dead pid fails silently. Isolation keeps a crash contained, but the rest of the system still has to find out about it. Erlang has two tools for that. Links tie the fate of two processes together. Monitors let one process watch another.

## Links

A plain `spawn` leaves the two processes unrelated. If the child dies, the parent is not told.

```erlang
1> self().
<0.84.0>
2> spawn(fun() -> exit(oops) end).
<0.87.0>
3> self().
<0.84.0>
```

`exit/1` from lesson 07 ends the calling process. The shell did not notice. `spawn_link/1` spawns and links in one step.

```erlang
4> spawn_link(fun() -> exit(oops) end).
** exception exit: oops
5> self().
<0.91.0>
```

A dying process sends an exit signal with its exit reason to every linked process. An abnormal reason kills the receiver, which then signals its own links. The shell process died with reason `oops` and was replaced, which is why `self()` changed.

Links are symmetric. It does not matter which side created the link. Here process A spawns and links to B, and B fails one second later.

```erlang
6> A = spawn(fun() ->
6>     spawn_link(fun() -> timer:sleep(1000), exit(b_failed) end),
6>     timer:sleep(infinity)
6> end).
<0.94.0>
7> timer:sleep(1200).
ok
8> is_process_alive(A).
false
```

`link/1` links the caller to an existing pid. Prefer `spawn_link`. With `spawn` followed by `link`, the new process can die in the gap between the two calls.

## Normal and Abnormal Exits

A process whose function returns exits with reason `normal`. So does `exit(normal)`. A `normal` exit signal does not kill linked processes.

```erlang
9> spawn_link(fun() -> ok end).
<0.99.0>
10> self().
<0.91.0>
```

Every other reason is abnormal. An uncaught error is one too. Its reason is a tuple of the error and the stack trace, such as `{badarith, [...]}`.

The rule suits processes that cooperate on one job. If a worker finishes, its partners carry on. If it crashes, they are probably waiting for something that will never arrive, so the whole group stops together.

## Trapping Exits

Some process has to survive in order to react. A process that sets the `trap_exit` flag is not killed by exit signals. Each signal is turned into a message of the form `{'EXIT', Pid, Reason}` and put in its mailbox. The quotes are needed because `EXIT` starts with an uppercase letter and would otherwise be a variable.

```erlang
11> process_flag(trap_exit, true).
false
12> spawn_link(fun() -> exit(oops) end).
<0.103.0>
13> spawn_link(fun() -> ok end).
<0.105.0>
14> flush().
Shell got {'EXIT',<0.103.0>,oops}
Shell got {'EXIT',<0.105.0>,normal}
ok
```

`process_flag/2` returns the old value of the flag. A trapping process also hears about `normal` exits.

## Stopping Another Process

`exit/2` sends an exit signal to any pid, linked or not, as if a linked process had died with that reason.

```erlang
15> W = spawn_link(fun() -> timer:sleep(infinity) end).
<0.108.0>
16> exit(W, shutdown).
true
17> flush().
Shell got {'EXIT',<0.108.0>,shutdown}
ok
```

A process that traps exits turns such a signal into a message and may ignore it. The reason `kill` is the exception. It cannot be trapped.

```erlang
18> Stubborn = spawn(fun() ->
18>     process_flag(trap_exit, true),
18>     receive Msg -> io:format("stubborn got ~p~n", [Msg]) end,
18>     timer:sleep(infinity)
18> end).
<0.112.0>
19> exit(Stubborn, please_stop).
stubborn got {'EXIT',<0.91.0>,please_stop}
true
20> is_process_alive(Stubborn).
true
21> exit(Stubborn, kill).
true
22> is_process_alive(Stubborn).
false
```

A killed process exits with reason `killed`, not `kill`, so the untrappable signal does not spread over its links. Ask with `shutdown` first and keep `kill` as the last resort.

## Monitors

A link is the wrong tool when you only want to watch. The chat room wants to know when a member dies, but a member should not die because the room crashed. `monitor/2` is one-way. It returns a reference, and when the watched process ends the watcher gets one `'DOWN'` message.

```erlang
23> process_flag(trap_exit, false).
true
24> P = spawn(fun() -> receive stop -> ok end end).
<0.119.0>
25> Ref = monitor(process, P).
#Ref<0.912032649.1470627848.93010>
26> P ! stop.
stop
27> flush().
Shell got {'DOWN',#Ref<0.912032649.1470627848.93010>,process,<0.119.0>,normal}
ok
```

The message is `{'DOWN', Ref, process, Pid, Reason}`. The watcher is never killed, and the watched process is not affected. Monitoring a pid that is already dead is safe. The message arrives at once with reason `noproc`.

`spawn_monitor/1` spawns and monitors in one step and returns `{Pid, Ref}`. `demonitor(Ref, [flush])` cancels a monitor. The `flush` option also removes a `'DOWN'` message that is already waiting in the mailbox.

| | Link | Monitor |
| --- | --- | --- |
| Direction | both ways | watcher to watched |
| On abnormal death | the other process dies, or gets `'EXIT'` if it traps | watcher gets `'DOWN'` |
| Use when | the processes cannot work without each other | one side needs to clean up or report |

## A Room That Forgets Dead Members

The room monitors every process that joins and stores the reference next to the name.

**Update `chat_room.erl`:**

```erlang
%% In chat_room.erl, replace loop/1 and send_all/2
loop(Members) ->
    receive
        {join, Pid, Name} ->
            Ref = monitor(process, Pid),
            send_all(Members, {chat, "room", Name ++ " joined"}),
            loop([{Pid, Name, Ref} | Members]);
        {leave, Pid} ->
            case lists:keyfind(Pid, 1, Members) of
                {Pid, _Name, Ref} -> demonitor(Ref, [flush]);
                false -> ok
            end,
            loop(lists:keydelete(Pid, 1, Members));
        {'DOWN', _Ref, process, Pid, _Reason} ->
            case lists:keytake(Pid, 1, Members) of
                {value, {Pid, Name, _}, Rest} ->
                    send_all(Rest, {chat, "room", Name ++ " disconnected"}),
                    loop(Rest);
                false ->
                    loop(Members)
            end;
        {broadcast, Pid, Text} ->
            case lists:keyfind(Pid, 1, Members) of
                {Pid, Name, _} -> send_all(Members, {chat, Name, Text});
                false -> ignored
            end,
            loop(Members);
        {call, From, Ref, members} ->
            From ! {Ref, lists:sort([Name || {_Pid, Name, _Ref} <- Members])},
            loop(Members)
    end.

send_all(Members, Message) ->
    [Pid ! Message || {Pid, _Name, _Ref} <- Members],
    ok.
```

`lists:keytake/3` returns the matching tuple and the rest of the list. A member who leaves is demonitored, so no `'DOWN'` arrives for them later.

```erlang
1> c(chat_room).
{ok,chat_room}
2> Room = chat_room:start().
<0.91.0>
3> chat_room:join(Room, "alice").
ok
4> Bob = spawn(fun() -> chat_room:join(Room, "bob"), receive stop -> ok end end).
<0.94.0>
5> chat_room:members(Room).
["alice","bob"]
6> exit(Bob, kill).
true
7> chat_room:members(Room).
["alice"]
8> flush().
Shell got {chat,"room","bob joined"}
Shell got {chat,"room","bob disconnected"}
ok
```

## Keeping a Worker Alive

Links and `trap_exit` are enough to restart a failed process. The keeper starts a worker with `spawn_link`, waits for its `'EXIT'` message, and starts a new one unless the exit was normal.

**Create `keeper.erl`:**

```erlang
-module(keeper).
-export([start/1, init/1]).

start(WorkerFun) ->
    spawn(?MODULE, init, [WorkerFun]).

init(WorkerFun) ->
    process_flag(trap_exit, true),
    loop(WorkerFun, spawn_link(WorkerFun)).

loop(WorkerFun, Worker) ->
    receive
        {'EXIT', Worker, normal} ->
            io:format("worker finished, keeper stops~n");
        {'EXIT', Worker, Reason} ->
            io:format("worker died: ~p. restarting~n", [Reason]),
            loop(WorkerFun, spawn_link(WorkerFun))
    end.
```

The worker registers a name, because its pid changes with every restart. It crashes when `Text` is not a string.

**Create `echo.erl`:**

```erlang
-module(echo).
-export([run/0]).

run() ->
    register(echo, self()),
    loop().

loop() ->
    receive
        {From, Text} ->
            From ! {echo, Text ++ "!"},
            loop();
        stop ->
            ok
    end.
```

```erlang
1> c(keeper), c(echo).
{ok,echo}
2> Keeper = keeper:start(fun echo:run/0).
<0.95.0>
3> whereis(echo).
<0.96.0>
4> echo ! {self(), 42}.
worker died: {badarg,[{erlang,'++',
                              [42,"!"],
                              [{error_info,#{module => erl_erts_errors}}]},
                      {echo,loop,0,[{file,"echo.erl"},{line,11}]}]}. restarting
{<0.84.0>,42}
5> whereis(echo).
<0.99.0>
6> echo ! {self(), "still there?"}.
{<0.84.0>,"still there?"}
7> flush().
Shell got {echo,"still there?!"}
ok
```

The VM also prints an error report, left out here. The worker has no `try ... catch` and no input validation. It crashed on bad input and was back at once under a new pid. This is "let it crash" from lesson 07 with the missing half filled in.

The keeper is a toy. A worker that crashes on startup is restarted in a tight loop forever. It manages one worker, and nothing watches the keeper itself. OTP supervisors solve this, and lesson 14 covers them.

## Key Takeaways

- **Links are symmetric**. An abnormal exit on either side kills the other side, and `normal` exits do not
- **`spawn_link`** creates the process and the link atomically, which `spawn` plus `link/1` cannot do
- **`process_flag(trap_exit, true)`** turns exit signals into `{'EXIT', Pid, Reason}` messages so a process can react and keep running
- **`exit(Pid, Reason)`** stops another process. `kill` cannot be trapped and shows up as `killed`
- **Monitors are one-way**. The watcher gets one `{'DOWN', Ref, process, Pid, Reason}` message and neither side is killed
- **`demonitor(Ref, [flush])`** cancels a monitor and removes a `'DOWN'` that already arrived
- **A process that traps exits and respawns its worker** is the core idea of a supervisor
